## 🧭 拖拽交互流程说明（供 Cursor 理解开发）

### 🗃️ 背景信息

* 所使用的拖拽库：`hello-pangea/dnd`
* 表名：`collection_lists`
* 数据结构：

  ```ts
  {
    id: string;
    name: string;
    parent_id: string | null;     // 嵌套结构的父子关系
    order_index: number;          // 同一层级内的排序，使用稀疏浮点数
    visibility: 'public' | 'unlisted' | 'private';
  }
  ```

---

## 🚚 拖拽交互流程详解

### ✅ 情况 1：在同一层级内拖动（排序）

#### 🧭 用户行为：

用户将列表 A 拖动到列表 B 的**上方或下方**，在同一父级下（即 parent\_id 相同）。

#### 🎨 前端 UI 表现：

* 拖动指示线出现，表示新位置
* 拖动项在列表中重新排序（同一层级内）

#### 🔄 后端处理：

更新数据库中的 `order_index` 字段，保持 `parent_id` 不变。

```ts
await supabase
  .from('collection_lists')
  .update({ order_index: newIndex })
  .eq('id', draggedId);
```

#### 💡 说明：

* 使用稀疏排序，例如 `10, 20, 30`，插入 `15` 可排在 10 和 20 之间。
* 若顺序间隔不足（如排序为 1.00001 和 1.00002），则会触发重排（见下方说明）。
* 拖动项如果包含子项，则一起移动，子结构不变。

---

### ✅ 情况 2：拖动成为另一个项的子项（嵌套）

#### 🧭 用户行为：

用户将 A 拖动**覆盖在 B 上**，表示 A 将成为 B 的子项。

#### 🎨 前端 UI 表现：

* 被覆盖项高亮或缩进
* 拖动项以子项形式展示在被嵌套目标下

#### 🔄 后端处理：

更新 `parent_id` 为目标项 `B.id`，并将 `order_index` 设置为其子项的末尾。

```ts
await supabase
  .from('collection_lists')
  .update({ 
    parent_id: targetId, 
    order_index: lastChildIndex + 10 
  })
  .eq('id', draggedId);
```

---

### ✅ 情况 3：拖动出原父级，成为顶级项

#### 🧭 用户行为：

用户将某个子项拖出父项边界，放置在主列表的空白处或其他顶层项之间。

#### 🎨 前端 UI 表现：

* 拖动项脱离原缩进，成为新顶层项
* 可能出现在顶级列表顶部或底部

#### 🔄 后端处理：

更新：

* `parent_id = null`
* 新的 `order_index`（根据顶层排序）

```ts
await supabase
  .from('collection_lists')
  .update({ 
    parent_id: null, 
    order_index: newIndex 
  })
  .eq('id', draggedId);
```

## 🔁 排序 & 重排逻辑说明（关键）

### 💡 为什么使用稀疏排序（sparse sorting）？

* 每个 sibling 节点之间间隔初始为 10，如：`10, 20, 30, ...`
* 拖动插入时计算新 index：`(prev + next) / 2`
* 减少整体重排，提升性能

### ⚠️ 什么时候触发“定期重排”？

当以下任一情况发生：

1. **order\_index 精度过细**：间隔小于设定阈值（如 < 0.0001）
2. **层级内多次排序插入**导致稀疏耗尽
3. **人为强制触发**（例如管理员操作或 API 调用）

### ✅ 重排操作

自动将该层级内所有子项：

```ts
const normalizedList = children.map((item, index) => ({
  ...item,
  order_index: (index + 1) * 10
}));
```

然后批量更新数据库。

## ✅ 数据库设计建议

### 字段说明（已更新）：

```ts
order_index NUMERIC DEFAULT 0   -- 支持小数稀疏排序
```

确保：

* 支持浮点数或高精度数值（Supabase 建议使用 NUMERIC 类型）
* 查询按 `parent_id, order_index` 排序时仍保持性能

## 🧱 拖拽逻辑对照表

| 拖拽行为   | UI变化   | parent\_id变化 | order\_index变化 | 说明        |
| ------ | ------ | ------------ | -------------- | --------- |
| 顶层内排序  | 顺序调整   | 不变           | 重新计算           | 同层级       |
| 拖入子项   | 缩进显示   | 设置为目标id      | 该子项末尾          | 成为子项      |

| 排序频繁稠密 | 无明显变化  | 不变           | 全体重排           | 自动或手动触发重排 |

## 🚀 重构后的功能特性

### ✅ 稀疏排序系统
- **初始间隔**: `SPARSE_INTERVAL = 10`
- **最小间隔阈值**: `MIN_INTERVAL = 0.1`
- **计算方式**: `(prev + next) / 2` 用于中间插入
- **自动重排**: 当间隔小于阈值时触发

### ✅ 子树移动
- **完整子树**: 父项拖动时，所有子项一起移动
- **结构保持**: 子树内部结构不变
- **parent_id 更新**: 正确更新子项的父子关系

### ✅ 智能嵌套判断
- **嵌套条件**: `overItem.level < activeItem.level`
- **排序条件**: 同层级或向更深层级移动
- **视觉反馈**: 清晰的拖拽指示

### ✅ 后端优化
- **批量更新**: 支持大量数据重排
- **分组处理**: 按 parent_id 分组执行重排
- **性能优化**: 减少数据库操作次数
